# Prior Art Research: Semantic Search Over Bookmarks / History / Read-Later Content

Research date: 2026-07-10
Scope: existing implementations of AI/semantic search over bookmarks, browsing history, or read-later archives — open-source repos, Chrome Web Store products, SaaS products, and dead/discontinued attempts. Compiled to inform the build of **Bookmark Semantic Search**, a local-first MV3 extension indexing ~1,300+ bookmarks with a local embedding model, loose semantic search, and auto-tagging.

## Per-Project Notes

### A. Open-source projects most directly instructive for this build

**Memex (WorldBrain)** — [github.com/WorldBrain/Memex](https://github.com/WorldBrain/Memex)
The closest long-running analog to "second brain browser extension," but it is full-text search, not vector/semantic search — AI features are a bolt-on chat/summarize layer, not the retrieval core. Its durability (4.7k★, active since ~2016, 13k+ commits) comes from a deliberate non-VC "Steward Ownership" funding model precisely to avoid the fate of Rewind/Heyday below.
Lessons: (1) full-text/keyword search alone is not "loose" enough for queries like "warmup iphone ai" — you need embeddings; (2) sustainable local-first tools intentionally avoid growth-at-all-costs funding, which correlates with survival; (3) annotation/highlight features expand scope far beyond search — resist scope creep for a v1.

**search-bookmarks-history-and-tabs (Fannon)** — [github.com](https://github.com/Fannon/search-bookmarks-history-and-tabs)
The best-engineered comparable MV3 extension in this space (330★, 48 releases, active in June 2026). Not semantic (uses uFuzzy fuzzy matching) but extremely disciplined about privacy (zero telemetry, no outside communication) and performance (explicitly documents that `historyMaxItems` and bookmark count affect init/search latency, and gives users levers: precise-mode fallback, disable highlighting, cap result count). It's a strong reference for MV3 popup UX (mode prefixes like `b=bookmarks`, `#tag`, `~folder`; Vim/Emacs-style keybindings) and for how to document performance tradeoffs honestly.
Lessons: (1) ship a fast non-semantic fallback path — perceived speed matters as much as search quality; (2) surface performance knobs to users rather than hiding scale limits; (3) local LLM tag-suggestion via the browser's own `LanguageModel` API is a viable zero-infra pattern to reuse for auto-tagging.

**gemma4-browser-extension (nico-martin)** — [github.com](https://github.com/nico-martin/gemma4-browser-extension)
The strongest architectural reference for exactly our stack: Transformers.js + WebGPU running inside a persistent MV3 background/service-worker context, with a React side-panel UI communicating via `chrome.runtime` messaging, and `all-MiniLM-L6-v2` embeddings stored in IndexedDB for a `find_history` semantic tool. 1.1k★ and actively developed — the most "senior" open-source example of the exact architecture pattern this project needs.
Lessons: (1) host the model in the background/service-worker so it loads once and is shared across UI surfaces instead of being re-downloaded/re-initialized per popup open; (2) `all-MiniLM-L6-v2` is a repeatedly-chosen default (also used by bookmark-lens, gemma4-browser-extension) — small, fast, good enough, wide ecosystem support; (3) separate content-script (DOM/page access) from background (inference) from UI (side panel) cleanly — mirrors MV3 constraints well.

**SemanticFinder (do-me)** — [github.com](https://github.com/do-me/SemanticFinder)
The most mature pure client-side transformers.js semantic search tool (324★). Directly documents the performance cliff: ~1-2 minutes to embed Moby Dick (660K chars) on a mid-range CPU, ~2 seconds per subsequent query. Explicitly recommends "a proper vector database instead" once you outgrow toy-scale in-memory search — relevant since 1,300+ bookmarks with page-metadata is a non-trivial corpus.
Lessons: (1) budget real wall-clock time for one-time initial indexing and communicate progress to the user; (2) WebGPU acceleration is worth gating behind capability detection since WASM-only fallback is meaningfully slower; (3) "hybrid search" (semantic + literal/full-text) is a recurring, valued feature across nearly every serious project in this space (Linkwarden, TraceMind, bookmark-lens, SurfMind, AI Bookmark Manager) — don't ship semantic-only.

**web-recall (tauki)** — [github.com](https://github.com/tauki/web-recall)
Honest, very early (0★, pre-1.0) project that depends on a locally-*running* Ollama HTTP server rather than in-browser inference — a materially different (heavier, less zero-config) architecture than transformers.js-in-browser. The README's frank admission that its "linear scan over stored embeddings... works for a few hundred pages but won't scale to thousands" is the single most quantified real-world data point found on when brute-force cosine similarity in JS starts to break down — squarely relevant at the ~1,300-bookmark scale this project targets.
Lessons: (1) requiring a companion local server (Ollama) is a real adoption tax vs. shipping the model inside the extension; (2) plan explicitly for the point where linear scan cosine similarity needs an ANN/index structure — 1,300 items is roughly in the zone this project flags as risky; (3) keep reranking/chat candidate sets small (5–10 items) for latency, if adding an "ask" feature later.

**bookmark-lens (cornelcroi)** — [github.com](https://github.com/cornelcroi/bookmark-lens)
Not a browser extension (it's an MCP server for Claude Desktop/Cursor), but the most complete reference for a fully local storage architecture: DuckDB for relational metadata + LanceDB for vectors, `all-MiniLM-L6-v2` embeddings, explicit cost transparency for the *optional* cloud-LLM enrichment tier (~$0.0005/bookmark), and CPU-only PyTorch to keep install size down.
Lessons: (1) separating relational metadata store from vector store is a clean pattern even in a browser context (e.g., chrome.storage/IndexedDB for metadata + a vector index for embeddings); (2) make any cloud-dependent enhancement feature explicitly optional and cost-transparent, never required for core search; (3) roadmap explicitly lists "browser extension" as future work — validates that MCP-first tools see browser extension as the natural next UX surface, not vice versa.

**semantic-bookmark-manager (dh1011)** — [github.com](https://github.com/dh1011/semantic-bookmark-manager)
Small, largely dormant (6 commits) Flask app, but its README calls out one sharp, easily-missed pitfall directly relevant to any project that might let users swap embedding models: **switching embedding models requires re-embedding everything**, because dimensionality/semantics differ between models. Worth designing around from day one (e.g., store the model id/version alongside each vector; invalidate/rebuild the whole index on model change rather than silently mixing vector spaces).

**Librarian (oto-labs)** — [github.com](https://github.com/oto-labs/librarian)
A near-exact prior attempt at this project's premise (Chrome extension, Sentence-BERT via transformers.js, Orama vector search, localStorage → OPFS), 197★ but stalled/abandoned with an honest TODO list (settings, accurate progress bar, smarter salient-text subselection, faster scraping, better UI/UX) never completed. The HN thread ([news.ycombinator.com/item?id=39171190](https://news.ycombinator.com/item?id=39171190)) shows users immediately asking for history search (not just bookmarks) and Firefox support, and links to Orama's OPFS-based storage as the fix for "everything in memory" scaling limits that plagued earlier vector-search-in-browser tools (e.g., Voy).
Lessons: (1) this is essentially a proof that the idea works technically but stalls on polish/completeness — a warning that "salient text subselection" (deciding what part of a scraped page to embed) and scraping robustness are where such projects die, not the embedding step itself; (2) OPFS > localStorage/in-memory for any nontrivial corpus size; (3) users immediately want browsing history too, so an early accept/decline on scope (bookmarks-only vs. bookmarks+history) is a governance decision to make explicitly.

**Pinbot** — [Chrome Web Store](https://chromewebstore.google.com/detail/pinbot/jbijbbnkaeclpmednjodmbdeobebiobg) / [HN launch](https://news.ycombinator.com/item?id=35974965)
Fully local (transformers.js, SQLite-in-OPFS), CPU-only at launch (pre-dated WebGPU support in transformers.js). The HN launch thread is the sharpest cautionary data point in this whole research set: real users reported **energy-impact scores in the thousands on macOS**, **8GB+ RAM usage within an hour**, and near-crashes, attributed to unthrottled MutationObserver-driven embedding generation running continuously in the background. The creator also candidly called MV3 "a remarkably hostile development environment" for porting to Firefox.
Lessons (highest-priority for this build, since Pinbot is the most architecturally similar prior attempt): (1) **never embed continuously/unthrottled in the background** — batch, debounce, and cap concurrent embedding work; (2) cache/dedupe aggressively ("only unknown sentences are converted to embeddings" was Pinbot's mitigation) — for a fixed 1,300-bookmark corpus this is easier than Pinbot's continuously-growing history use case, since indexing is a bounded one-time-plus-incremental job, not a live firehose; (3) test power/memory impact explicitly before shipping, since Chrome Web Store reviewers and users will surface this immediately and it's reputation-damaging.

**Ask_your_Bookmarks / semantic-bookmark-manager / SurfMind pattern**
A recurring failure mode across several smaller open-source and closed attempts: shipping "local-sounding" bookmark search that actually calls a cloud embedding API (Gemini) per bookmark or per query, or does hybrid local-capture/cloud-inference (SurfMind). This undercuts the core "zero recurring cost, local-first" pitch these tools otherwise market, and is exactly the trap to avoid for this project's positioning.

### B. Polished commercial products (UX patterns to learn from)

**Raindrop.io + Stella** — the most mature "semantic search over bookmarks" product at scale. Notable trajectory: semantic search was shipped, found to have quality issues, **disabled**, then re-shipped "much improved" — a candid signal that naive embedding-search-over-short-bookmark-metadata is genuinely hard to get right on the first pass (relevant since our corpus is title/URL/light metadata, not full page text). Stella (Feb 2026) shows the direction the category is heading: natural-language bulk operations ("tag and sort these," "merge duplicate tags") layered on top of search, not just retrieval. Pricing: semantic search gated to a cheap Pro tier ($3/mo); this project's "zero recurring cost" pitch is a direct differentiator against this.

**mymind** — best-in-class visual/associative UX (color search, OCR'd screenshot text, "serendipity mode"), explicitly designed around *zero manual organization*. Consistently cited (Product Hunt, comparison blogs) as beating Raindrop on design/AI tagging while losing on flexibility/price/import-export. Relevant as the design-quality bar ("Apple-style minimal UI") this project should aim for, even though mymind is a full cross-content-type app, not bookmark-only.

**Fabric (fabric.so)** — closest positioning to "search by meaning, not just title" for saved links; saves full page content so search survives link rot. PH reviews explicitly compare it favorably to mymind/Notion/Obsidian on stickiness. Downsides cited: onboarding/desktop bugs, no clear local export/storage story — a trust gap this project's local-first architecture directly addresses as a selling point.

**TraceMind** — the most direct "local-first, on-device AI, MV3, no account" positioning found in the entire research set, but for *history* not bookmarks. Its own comparison page ([tracemind.app/compare](https://tracemind.app/compare)) is itself a useful, up-to-date competitive map of this category (Chrome built-in history, Heyday, Memex, Microsoft Recall, Rewind, SurfMind, Recall.ai, mymind) and explicitly markets local-only storage as the safeguard against the Heyday/Rewind failure mode. Pricing ($5/mo Pro, generous free tier) is a plausible model if this project ever needs monetization, though the stated goal here is zero recurring cost.

**Recall (getrecall.ai)** — strong "augmented browsing" idea (relevant saved content resurfaces contextually as you browse) and spaced-repetition/quiz features for retention — outside this project's scope but a notable UX idea for a future "resurface forgotten bookmarks" feature. 500K+ users, 4.1★, but is fully cloud-based.

**SurfMind** — markets itself as local but actually round-trips to a server for the AI-heavy steps ("ingests locally stored data, converts it into vector embeddings, sends it to the server..."). A competitor's comparison explicitly calls this out as a trust gap versus true local-first tools. Reinforces that "local" claims get scrutinized and should be architecturally true, not just marketing language.

### C. Built-in browser/OS features (the biggest long-term competitive threat)

**Chrome's own built-in AI history search** ([support.google.com/chrome/answer/15305774](https://support.google.com/chrome/answer/15305774)) — Google has already shipped on-device semantic history search directly in Chrome (US, English-only as of this writing). Important scope note: it explicitly covers **history, not bookmarks**, only indexes pages visited *after* the feature is enabled, requires 2+ word "detailed" queries to trigger AI matching, and shows at most 3 results. This is simultaneously validation (Google agrees on-device embedding search over browsing signals is valuable) and a warning: if Google extends this to bookmarks or global rollout, a big chunk of the addressable need disappears. This project's differentiators versus that risk: works today across all bookmarks (not just post-enablement), not geo/language gated, richer result count, and (per project goals) auto-tagging which Chrome's native feature doesn't offer at all.

**Microsoft Recall** — OS-level (Windows Copilot+ PCs), screenshots everything and lets you search it semantically on-device. Not bookmark-specific, but the highest-profile precedent for the privacy scrutiny this entire category attracts (delayed launch, security researcher backlash) before eventually shipping with encryption and opt-in controls. Relevant lesson: be conspicuously clear and minimal about what's captured/stored/sent, from day one — the category is primed for privacy skepticism.

### D. Failed / discontinued attempts and why

**Rewind.ai → Limitless** — the starkest cautionary tale in this research. Rewind's entire pitch was "your data stays on your device" (local-first screen recording + search). Parent company Limitless pivoted to a hardware wearable (the Pendant), was **acquired by Meta**, and Meta shut down the original local-first Mac app on **December 19, 2025** to refocus on wearables — even wiping data for users in several regions (Brazil, China, EU, Israel, South Korea, Turkey, UK) with only a short export window. The irony noted by commentators: a "your data never leaves your device" product's data ultimately became Meta's, and the desktop product users actually relied on was simply discontinued once it no longer served the acquirer's strategic goal.
Lesson: local-first architecture protects users' *data* but does not protect the *product's survival* if it's VC-funded and pivots/gets acquired. Reinforces the value of this project being a self-contained, ownable artifact (a personal extension) rather than depending on a company's roadmap.

**Heyday** — an AI "second brain"/browsing-copilot with real funding ($6.5M seed, 2022) whose trajectory is murkier: marked inactive by third-party AI-tool directories in late 2024, yet still showing some Product Hunt activity into 2026. Recent user reviews cite **product stagnation** (search interface not improving), **increasing extension friction/annoyance**, and **login/reliability failures** — a slow fade rather than a clean shutdown.
Lesson: cloud-dependent "memory" products die by neglect as much as by explicit shutdown; reliability regressions (login failures, sync bugs) are what users notice first and are exactly the class of bug a local-first, no-account architecture sidesteps entirely.

**Librarian, web-recall, Ask_your_Bookmarks** (see section A) — smaller-scale "died on the vine" open-source attempts at almost exactly this project's premise. None failed for lack of technical feasibility (all proved the core embedding pipeline works); they stalled on unglamorous completion work: scraping robustness, progress/UX polish, and — for web-recall specifically — a documented scaling ceiling around "a few hundred" to "thousands" of items using naive linear-scan cosine similarity in the browser.

## Top 10 Takeaways for Our Build

1. **The core technical pattern is proven and has a clear reference architecture.** `gemma4-browser-extension` demonstrates the right MV3 shape: model hosted in the background/service-worker (loaded once, shared across UI), side panel or popup as a thin messaging client, content script isolated to DOM access. Follow this shape rather than re-deriving it.

2. **`all-MiniLM-L6-v2` (or similarly small sentence-transformer models via transformers.js) is the de facto standard local embedding model** for this exact use case — chosen independently by `gemma4-browser-extension`, `bookmark-lens`, and implicitly by `Librarian`/Pinbot (Sentence-BERT family). It's small, fast, WASM/WebGPU-compatible, and "good enough" — don't over-invest in model selection for v1.

3. **Never embed continuously/unthrottled.** Pinbot's HN launch is a direct warning: unbatched, un-debounced background embedding generation caused multi-gigabyte RAM usage and near-crashed users' machines, badly damaging launch reception. For a *fixed* ~1,300-bookmark corpus, this project has it easier than history-tracking tools — indexing is a bounded, mostly one-time job plus small incremental deltas, not a live firehose. Design it that way explicitly (batch, cap concurrency, background-idle scheduling) and it becomes a real advantage.

4. **Naive linear-scan cosine similarity in-browser has a documented ceiling** — web-recall's README states plainly that its approach "works for a few hundred pages but won't scale to thousands." At ~1,300+ bookmarks we sit right at that edge; budget for either an efficient linear scan (typed arrays / WASM SIMD, which is often fine up to low-thousands of short vectors) or a lightweight ANN index (Orama, as used by `Librarian`) rather than assuming naive JS loops will stay fast.

5. **Ship hybrid search (semantic + literal/keyword), not semantic-only.** Nearly every serious project in this space (Linkwarden, TraceMind, SurfMind, SemanticFinder, AI Bookmark Manager) offers both, because pure semantic search alone under-serves exact-match/URL/title lookups. `search-bookmarks-history-and-tabs`'s mode-prefix UX (`b=`, `#tag`, `~folder`) is a good lightweight pattern for blending modes without a mode switcher UI.

6. **Version/tag every vector with the embedding model that produced it.** `semantic-bookmark-manager`'s README flags a real trap: switching models silently breaks search because vector spaces aren't compatible across models. Store a model-id/version field per vector and force a full reindex on model change — cheap to build in now, painful to retrofit.

7. **"Local" claims get scrutinized — be architecturally true, not just marketing-true.** SurfMind is called out by a competitor for claiming local-first while round-tripping to a server for the actual embedding/search step. Since zero-recurring-cost and local-first are this project's core differentiators, make sure no step of the search path silently depends on a network call.

8. **OPFS/IndexedDB, not localStorage, for the vector index.** `Librarian`'s HN thread and its own storage evolution (localStorage → OPFS) confirm this: localStorage's ~5-10MB quota and synchronous API don't hold up for a real embedding index; OPFS (as Pinbot also uses, backing a SQLite file) is the right target for anything beyond toy scale.

9. **Auto-tagging can reuse the browser's own on-device LLM instead of a bespoke model.** `search-bookmarks-history-and-tabs` demonstrates a zero-infrastructure pattern: call the browser's built-in `LanguageModel` API (Chrome's on-device Gemini Nano-class model) for tag suggestions, keeping the "no server, no API key" promise intact for that feature too, not just for embeddings.

10. **The category's biggest structural risks are (a) Chrome/Google absorbing this feature natively and (b) products dying from neglect, not technical failure.** Chrome already ships on-device semantic *history* search (though not bookmarks, and gated to US/English with a 3-result cap) — a real long-term threat surface to monitor. Meanwhile Rewind (killed by acquisition) and Heyday (killed by stagnation) show that even well-funded "local-first memory" products don't survive as companies. This project's advantage is structural: as a self-contained personal extension with no server and no company to shut it down, it is immune to both failure modes — that's worth stating explicitly as the project's value proposition, not just an implementation detail.
